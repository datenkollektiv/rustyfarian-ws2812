## [Unreleased]

### Added

- `rustyfarian-esp-hal-ws2812`: example `hal_c3_comet_under_load_async` (`--features embassy,esp-println`): the 12-LED async comet under a 10 kHz timer interrupt and a CPU-hogging task, cycling four load modes and logging frame errors, send time, frame interval and the worst interrupt gap per second — quantifies what critical-section frames cost other interrupts (radio tests stay downstream)
- `rustyfarian-esp-hal-ws2812`: example `hal_c3_rainbow_comet_async` (`--features embassy,esp-println`): a continuous 12-LED async animation on an ESP32-C3 (GPIO4) that logs transmit errors, send-time min/mean/max and the longest frame interval once per second — the workload of an async LED clock, where every frame takes the critical-section path
- `rustyfarian-esp-hal-ws2812`: `esp32s3` chip feature (forwarded to esp-hal, `esp-bootloader-esp-idf`, optional `esp-rtos` and `esp-println`) mirroring the existing `esp32` feature. Compile-verified on `xtensa-esp32s3-none-elf` and hardware-validated on the CrowPanel 1.28" (2026-10-14); library code unchanged (no chip-specific configuration)
- `rustyfarian-esp-hal-ws2812` and `rustyfarian-esp-idf-ws2812`: new examples for ESP32-S3 (`hal_s3_pulse` blocking, `hal_s3_pulse_async` async with `--features embassy`, `idf_s3_rainbow`) using the Elecrow CrowPanel 1.28" rotary knob (5-LED onboard ring on GPIO48). `idf_s3_rainbow` also supplies the IDF v5.3.3 bootloader that `scripts/ensure-bootloader.sh` builds for `just run hal_s3_*`, the same pattern as C3/C6/ESP32. `hal_s3_pulse_async` pulses only the first LED, as `AsyncStatusLed` drives a single status LED
- Build tooling: `scripts/build-example.sh`, `run-example.sh`, `ensure-bootloader.sh` gained an `s3` chip arm (`xtensa-esp32s3-none-elf` / `xtensa-esp32s3-espidf`). Xtensa (`cargo +esp`, `-Zbuild-std=core`) now covers both `esp32` and `s3`. Corrected a stale comment: USB-Serial-JTAG was wrongly called "RISC-V only" (the S3 is Xtensa and has it; only the classic ESP32 lacks it)
- CI: `cross-target-xtensa.yml` now checks the ESP32-S3 alongside ESP32; `buildtargets: esp32,esp32s3` and a new cache key `...-1.97.0.0-esp32-esp32s3`. New recipe alias `just build-example-s3-hal` for quick S3 example builds
- `just check-hal-xtensa` now compile-checks the ESP32-S3 library and examples alongside ESP32
- `rustyfarian-esp-hal-ws2812`: `LongFramePolicy` enum (`CriticalSection` default, `Reject`, `Poll`) with `Ws2812Rmt::with_long_frame_policy` and `long_frame_policy` getter, selecting how the blocking and async drivers send frames longer than one RMT channel's RAM. `Poll` busy-polls the refill with interrupts live, bounded by the same timeout; it is not radio-safe and is meant for long strips on firmware without a radio (see [ADR 010](docs/adr/010-interchangeable-driver-semantics.md))
- `rustyfarian-esp-hal-ws2812`: `pub const WS2812_RESET_US: u32 = 280`, the minimum low time between frames that both drivers enforce (see the crate docs, "Frame spacing (latch)")
- `rustyfarian-esp-hal-ws2812`: `Ws2812Rmt::set_pixels_slice_masked` (blocking) runs the transmit and its refill polling inside `critical_section::with`, so interrupts cannot delay a long frame; about 0.36 ms of interrupts-off time for 12 LEDs. An earlier implementation (a critical section around an unbounded wait) was benched clean with Wi-Fi active on the ESP32-C3 downstream; the current bounded implementation awaits re-validation
- `rustyfarian-esp-hal-ws2812`: `tx_channel_config()` returns the RMT TX channel configuration the driver requires for an 80 MHz RMT source (`RMT_CLK_DIV`, idle output held low, no carrier), and `tx_channel_config_for(source)` derives the divider for the 10 MHz timing clock from any source rate passed to `Rmt::new`, returning `Error::RmtConfig` when no exact divider exists; and `Ws2812Rmt::from_channel_creator(creator, pin)` configures a channel and wraps it in one call, mapping esp-hal's `ConfigError` to `Error::RmtConfig`; consumers no longer copy the channel setup. Requested from the downstream `rustyfarian-rgb-clock` project
- `rustyfarian-esp-hal-ws2812`: `Error::ChannelLost`, returned by the blocking call that gives up its RMT channel after a failed drain and by every call after it, so consumers can tell a single failed frame (`Error::Transmit`) from a driver that must be rebuilt. Requested by the downstream `rustyfarian-rgb-clock` re-bench, whose `Poll` run could not tell the two apart
- `rustyfarian-esp-hal-ws2812`: `Error` implements `core::error::Error`, so `?` into `anyhow` or `&dyn Error` works the same with both ESP drivers
- `rustyfarian-esp-idf-ws2812`: `pub const WS2812_RESET_US: u32 = 280`; the driver now waits for the remainder of that interval before a frame that follows the previous one too closely (busy-wait of at most 280 µs with `Ets::delay_us`), matching the esp-hal driver. The crate docs and README gain a "Long frames and radios" section: the RMT ISR refill tolerates task latency but is not hard real time. They warn against `CONFIG_RMT_ISR_IRAM_SAFE=y`, which makes `Ws2812Rmt::new` fail with `ESP_ERR_INVALID_ARG` because esp-idf-hal 0.47 registers a transmit-done callback that lives in flash; when the setting is on, an `ESP_ERR_INVALID_ARG` from the constructor names it as the likely cause. With the default, a downstream ESP32-C3 bench kept a 12-LED ring clean through an OTA download
- `rustyfarian-esp-hal-ws2812`: example `hal_c3_frame_sweep_async` (`--features embassy`), which cycles 1, 2, 3, 12 and 64-LED frames under each `LongFramePolicy` for logic-analyser capture. It covers back-to-back frames, including a 1-LED case, and a cancellation phase that drops an async transmit mid-frame
- `pennant`: `SimpleLed` now honours `Polarity` — a new `SimpleLed::with_polarity(Polarity)` builder (default `ActiveHigh`, so existing behaviour is unchanged) lets active-low LEDs, such as the blue LED on GPIO8 of the ESP32-C3 SuperMini, light when the colour exceeds the threshold; `SimpleLed::new` and `SimpleLed::with_threshold` keep their signatures, and the `Polarity` enum moves to a private `polarity` module while remaining exported as `pennant::Polarity`

### Changed

- `rustyfarian-esp-hal-ws2812`: **Breaking (behaviour):** the blocking driver now follows `LongFramePolicy` too. `set_pixels_slice` and `SmartLedsWrite::write` send frames longer than one channel's RAM with interrupts masked by default (about 0.36 ms for 12 LEDs, 1.9 ms for 64), matching the async driver; frames that fit in channel RAM, including `set_pixel`, are unchanged. The refill polling of long blocking frames (and `set_pixels_slice_masked`) is now bounded by the same timeout as the async path (about 2 µs per pulse code plus 1 ms), which bounds the interrupts-off window: on timeout the driver leaves the critical section and keeps polling with interrupts live for a second timeout. If the frame ends (likely garbled), it returns `Error::Transmit` with the channel kept; if it does not, the transaction is dropped, which stops the channel, and the driver has no channel left, and that call and every later one return the new `Error::ChannelLost` (plain `Error::Transmit` always means the frame failed but the driver is still usable); rebuilding it needs an `Rmt` created from `peripherals.RMT.reborrow()` (and a reborrowed pin), otherwise only a reset recovers. The call is therefore bounded, except on a classic ESP32 whose RMT never reaches its end marker, where esp-hal's stop spins. **Breaking:** `CriticalSection` frames whose estimated masked time (1.3 µs per pulse code) exceeds `DEFAULT_MAX_NOMINAL_MASKED_US` (1000 µs, 32 LEDs; the ceiling limits this nominal estimate, not the actual interrupts-off time, which a stalled refill can stretch to the timeout) now return `Error::FrameTooLong` in both modes instead of masking interrupts for longer; raise or lift the ceiling with `with_max_nominal_masked_us`, or choose `Poll`. A downstream re-bench of commit `f53c5e8` (ESP32-C3, 12 LEDs, Wi-Fi active, built without `ESP_HAL_CONFIG_PLACE_RMT_DRIVER_IN_RAM`) rendered default `set_pixels_slice`, `SmartLedsWrite::write` and `set_pixels_slice_masked` clean with no driver errors; `Poll` garbled as documented, and the ceiling refused frames with `FrameTooLong`. A second downstream run at `c85a61a` with per-second logging found `Poll` under Wi-Fi keeps its channel (23 `Transmit`, 0 `ChannelLost` in 8,419 frames) and the default path still clean. Async, other chips, longer strips, a waveform capture and the drop/rebuild path are not yet validated. `set_pixels_slice_masked` keeps masking every frame regardless of length and policy, and is not capped. Long non-radio strips that cannot afford the masked window choose `LongFramePolicy::Poll`. Requested from the downstream `rustyfarian-rgb-clock` project, which runs the same clock on both ESP drivers. See [ADR 010](docs/adr/010-interchangeable-driver-semantics.md) and [`docs/features/driver-interchangeability-v1.md`](docs/features/driver-interchangeability-v1.md)
- `rustyfarian-esp-hal-ws2812`: the optional `esp-println` feature now uses esp-println's `auto` transport instead of `jtag-serial`. Output goes to the native USB-Serial-JTAG port when a host is attached there, otherwise to UART0, so boards whose USB socket is a USB-UART bridge (CH340, CP210x) and the classic ESP32 now show `println!` output
- `rustyfarian-esp-hal-ws2812`: **Breaking:** split the `async` feature in two. `async` now gates only the `Ws2812Rmt<'d, Async, N>` impl blocks and pulls in no runtime (only `critical-section`, already in esp-hal's graph); the new `embassy` feature implies `async` and pulls in `esp-rtos`, `embassy-time`, `embassy-executor` and `embassy-sync`. All six `*_async` examples and the `build-example` / `run-example` scripts switched to `--features embassy`. Consumers who relied on `async` to pull in the runtime must add `embassy`; consumers on another executor keep `async` and drop the runtime graph. Requested from the downstream `rustyfarian-peripherals` project, which uses the same split. See [`docs/features/esp-hal-async-feature-split-v1.md`](docs/features/esp-hal-async-feature-split-v1.md) and the ADR 008 update
- `rustyfarian-esp-hal-ws2812`: **Breaking:** `Error` is now `#[non_exhaustive]` and gains `FrameTooLong`, returned by the async driver under `LongFramePolicy::Reject`. Downstream `match` expressions need a wildcard arm
- `rustyfarian-esp-hal-ws2812`: both drivers now enforce the 280 µs latch between frames (`set_pixel`, `set_pixels_slice`, `SmartLedsWrite::write`). Short async frames (fit in channel RAM) carry the latch in the signal, so they complete about 280 µs later and use no CPU wait. Long frames on the critical-section path and blocking frames busy-wait only when frames come faster than 280 µs, in the caller's interrupt state. The wait needs esp-hal's `rt` feature; without it the wait gives up after about 1000 unchanged timer reads. A cancelled async transmit also schedules the latch wait for the next frame
- `rustyfarian-esp-hal-ws2812`: `critical-section` is a regular dependency instead of one enabled by `async`, so the crate always carries it; the masked paths need its implementation from esp-hal's `rt` feature
- `rustyfarian-esp-hal-ws2812`: the long-frame polling loop is placed in RAM with `#[esp_hal::ram]`, and it reads the clock every 16 polls instead of every poll, so a timeout overshoots by a few microseconds at most; the long-frame path is otherwise unchanged

### Fixed

- `rustyfarian-esp-hal-ws2812`: a blocking transmit that esp-hal refuses to start no longer leaves the driver without a channel. esp-hal 1.2.2 hands the channel back with the error, and the driver now keeps it, so later frames can still be sent
- Documentation: the usage snippets in `README.md` and the `pennant`, `rustyfarian-esp-hal-ws2812` and `rustyfarian-avr-ws2812` READMEs still pinned `"0.6"` a month after the 0.7.0 release, so copy-paste users resolved the previous release (`^0.6` never matches 0.7.0). Bumped to `"0.7"` and added the snippets, the root `[workspace.dependencies]` pins and the AVR example lockfile to the Version Bump checklist in `release-plan.md`
- CI: `just deny` failed on RUSTSEC-2024-0449 (`unsafe-libyaml` unmaintained), reached via `serde_yaml` <- `esp-config 0.8.0`. The advisory is now ignored in `deny.toml` with rationale: `serde_yaml` is enabled only by `esp-config`'s `build` feature, which `esp-hal` and `esp-bootloader-esp-idf` request solely as a build-dependency, so the parser runs in host build scripts and never reaches firmware. No upstream fix exists yet (`esp-config 0.8.0` is the latest release)
- CI: `cross-target-avr-upstream` no longer deletes `Cargo.lock` before building against upstream `avr-hal`. Deleting it re-resolved every transitive registry dependency, so the job reported unrelated crate churn as upstream breakage — it had been red since 2026-09-07 because `encoding_rs 0.8.40` (reached via `yaml-rust2`) calls `slice::as_chunks`, stabilised in Rust 1.88.0 on 2025-06-26 and therefore still unstable on the pinned `nightly-2025-04-27`, while `avr-hal` itself was fine throughout. Dropping the `rev` pin alone is enough to re-resolve the three avr-hal git packages against the branch tip; registry dependencies now stay at their locked versions, so a failure means upstream `avr-hal` genuinely moved
- `rustyfarian-esp-hal-ws2812`: async `set_pixels_slice` frames longer than one RMT channel's RAM (more than 1 LED on ESP32-C3, ESP32-C6 and ESP32-S3, more than 2 LEDs on ESP32) now have executor latency removed from their refill path, which had shifted the picture when the executor was late. The default `LongFramePolicy::CriticalSection` busy-polls such frames with interrupts masked; it does not guarantee the waveform, because flash-cache misses, flash stalls on the other core and high-priority Xtensa interrupt levels can still delay a refill. The blocking driver follows the same policy (see Changed). A downstream bench (ESP32-C3, 12 LEDs) saw `CriticalSection` frames garble only with Wi-Fi active, and clean frames once the firmware was built with `ESP_HAL_CONFIG_PLACE_RMT_DRIVER_IN_RAM=true`; the crate cannot detect that setting, so radio firmware must enable it. The cost is about 0.36 ms of interrupts-off time for 12 LEDs and 1.9 ms for 64, which can disturb Wi-Fi, ESP-NOW and UART on long strips, and the executor does not run other tasks during such a frame. The timeout (about 2 µs per pulse code plus 1 ms) bounds that time on every chip, including the classic ESP32, where the cleanup of an unfinished transmit spins until the end marker and now runs after the critical section. Adds `critical-section` as a regular dependency; firmware needs esp-hal's `rt` feature (or another implementation) to link. Hardware waveform validation is still pending. Requested from the downstream `rustyfarian-rgb-clock` project (12 LEDs, ESP32-C3) and a second downstream project (64 LEDs, ESP-NOW). See [`docs/features/esp-hal-async-long-frame-refill-v1.md`](docs/features/esp-hal-async-long-frame-refill-v1.md)

## [0.7.0] - 2026-09-25

### Added

- `pennant`: `RgbGpioLed` adapter (behind the `hal` feature) that drives a discrete, non-WS2812 RGB LED over three separate `embedded-hal` 1.0 `OutputPin`s, switching each channel on/off from an `RGB8` colour via a per-channel brightness threshold (eight on/off colours, not analog colour mixing); a new `Polarity` enum selects common-anode (`ActiveLow`) or common-cathode (`ActiveHigh`, default) wiring, covering boards like the Cheap Yellow Display (ESP32-2432S028R) whose onboard RGB LED is active-low on GPIO 4/16/17
- `pennant`: `channel_on(value, threshold)` — pure per-channel threshold helper (strict greater-than) alongside the existing `exceeds_threshold`
- `pennant`: `RgbPwmLed` adapter (behind the `hal` feature) — drives a discrete, non-WS2812 RGB LED over three `embedded-hal` 1.0 `SetDutyCycle` PWM channels, mapping each `RGB8` component onto a duty-cycle fraction for **smooth analog colour mixing** (true brightness control, unlike `RgbGpioLed`'s eight on/off colours); shares the `Polarity` flag with `RgbGpioLed` for common-anode (`ActiveLow`) / common-cathode (`ActiveHigh`, default) wiring
- `rustyfarian-esp-idf-ws2812`: two discrete-RGB-LED examples, both using the Cheap Yellow Display's RGB GPIO numbers 4/16/17 and defaulting to an external common-cathode LED (`ActiveHigh` — set `ActiveLow` for the CYD's common-anode onboard LED). `idf_esp32_rgb_cycle` drives `pennant`'s `RgbGpioLed`, cycling the eight on/off colours for on-hardware verification (`just build-example-esp32-rgb`, `just run idf_esp32_rgb_cycle`, example-only `rgb-gpio` feature); `idf_esp32_rgb_pulse` fades the LED in and out with `PulseEffect` via `RgbPwmLed` over three ESP-IDF LEDC PWM channels, so the effect renders as a smooth brightness fade rather than a blink (`just build-example-esp32-rgb-pulse`, `just run idf_esp32_rgb_pulse`, example-only `rgb-pwm` feature). Both features pull in `pennant/hal`
- Build tooling: persistent Cargo `build.build-dir` split for IDF builds (adopted; see [`docs/features/separate-build-environments-v1.1.md`](docs/features/separate-build-environments-v1.1.md)) — the bulky `esp-idf-sys` CMake tree relocates to `~/Library/Caches/rustyfarian-cargo-build/<workspace-hash>` while IDF final artifacts stay on the RAM disk. Resolved by `scripts/idf-build-dir.sh` and threaded through every IDF recipe. Override the cache location with `RUSTYFARIAN_IDF_BUILD_DIR`. Hardware-flash confirmation is still outstanding
- Build tooling: `just clean-idf-cache` removes the relocated persistent IDF build cache, and `just idf-build-dir-info` prints the resolved build-dir / `--config` flag / glob and whether the cache is materialised
- Build tooling: `just clean-idf-stale` — removes superseded `esp-idf-sys-*` build directories while keeping the newest per target, fixing the `multiple IDF-built bootloaders found` flash error without the full rebuild that `clean-idf-cache` forces. A dependency bump rehashes `esp-idf-sys` for every IDF target at once but each target only grows a second directory when next built, so the error recurs per architecture; this recipe sweeps them all
- CI: cross-target workflows gating all three embedded targets, which previously had **no** CI coverage at all — `cross-target-riscv.yml` (ESP32-C6 `riscv32imac` via `just check-hal`, plus ESP32-C3 `riscv32imc` via the new `just check-hal-c3`), `cross-target-avr.yml` (`just check-avr-target` / `check-avr-target-bitbang`, plus `just build-avr-example-all-bins` — the driver crate is lib-only, so only the example binaries exercise the AVR linker and `-C target-cpu=atmega328p`), and `cross-target-xtensa.yml` (`just check-hal-xtensa` on the Xtensa Rust toolchain, pinned to 1.97.0.0 and cached). Each is path-filtered to its own crates so the expensive Xtensa install stays off unrelated PRs; all three call existing `just` recipes so CI and local runs stay identical. See [`docs/features/cross-target-ci-v1.md`](docs/features/cross-target-ci-v1.md)
- CI: `cross-target-avr-upstream.yml` — a weekly (and manually dispatchable) job that drops the `arduino-hal` pin and builds the AVR example against upstream `avr-hal` main, via the new `just build-avr-example-upstream`. Pinning made PR builds reproducible but would have hidden upstream breakage, which the AVR gate exists partly to catch; this restores that signal without sacrificing reproducibility. A failure here means upstream moved, not that this repo is broken
- `examples/avr-nano-rainbow`: `arduino-hal` is now pinned to `rev = "e5c8f37fe484…"` and the package's `Cargo.lock` is committed (via a `.gitignore` negation), making the AVR CI job reproducible. `avr-hal` publishes nothing to crates.io and ships no tags or releases, so a commit SHA is the only available ref — and it is the same SHA the official `avr-hal-template` pins, so the previous bare `git = …` dependency was a deviation from upstream's own documented practice. `just build-avr-example-all-bins` now passes `--locked` so CI fails loudly if the manifest and lockfile drift apart
- `justfile`: `check-hal-c3` — checks the esp-hal driver on the ESP32-C3 target (`riscv32imc`, no atomics), including its examples. `check-hal` covers the C6/`riscv32imac` default-feature configuration, so the C3 build had no equivalent check
- `rustyfarian-esp-hal-ws2812`: `hal_c6_onboard_pulse` example — pulses the onboard SK68XXMINI LED on **GPIO8** of an ESP32-C6-DevKitC-1, requiring no external wiring. Exists as a standing regression guard: GPIO8 has a documented history of hanging in `txn.wait()` on the first transmit (fixed upstream in `esp-hal 1.1.0` with no workaround on our side), and every other `hal_c6_*` example targets GPIO18, so the pin had no coverage. Build with `just build-example hal-ws2812 hal_c6_onboard_pulse`, flash with `just flash hal_c6_onboard_pulse`
